# Wallet and payment query performance

The wallet and payment PostgreSQL integration suites enable `pg_stat_statements`
in their disposable database, reset it before and after provisioning, and record
executed SQL shapes touching FSDM or transaction tables. The raw per-shape call,
time, row and buffer counts are written to:

- `wallet/target/performance/wallet-setup-queries.csv`
- `payments/target/performance/payments-setup-queries.csv`
- `wallet/target/performance/wallet-postgres-queries.csv`
- `payments/target/performance/payments-postgres-queries.csv`

The setup snapshots cover enterprise updates and authorized test provisioning;
the runtime snapshots start after provisioning. Both include supporting FSDM
service SQL, so a row in these files is not necessarily wallet/payment-owned.

Payment tests also write `payments/target/performance/payments-postgres-plans.txt`
with `EXPLAIN (ANALYZE, BUFFERS)` for balance, bounded history, provider-reference
claim and settlement lookup. The final section compares bounded history on a
disposable 9,000-row copy with the filter index and with the history-order index.
These files are generated by the tests and are not deployment artifacts.

Run the wallet and payment suites with Docker available, using the commands in
their API documentation. Neither test invokes a real provider. The measurements
include SQL executed by the production EntityAssist services and current row
authorization, including retries and concurrent spending. They exclude host
authentication, network provider latency, and production database load.

On the 28 September 2026 fixture, payment setup covered 46 normalized SQL
shapes and 4,730 calls; wallet setup covered 39 shapes and 4,413 calls.
Payment runtime covered 96 shapes and 9,590 calls; wallet runtime covered 58
shapes and 2,275 calls. Current provider installation and grant joins were the largest
database CPU contributors (roughly 0.8–1.3 ms per call). The highest individual
arrangement-lock time came from the concurrent-spending tests, so it is a lock
wait rather than evidence of a slow lookup. Balance uses an arrangement/unit
index; the provider-reference claim uses the
existing FSDM value index; settlement lookup uses the existing parent Event index.

With 9,000 synthetic history rows, the prior filter index plus sort took about
1.03 ms for the first 50 entries. An index on `(arrangement_id, unit,
warehousecreatedtimestamp DESC, entry_id)` took about 0.025 ms in the same
test. The index is now declared in the managed core `16.transactions.sql` migration.
These timings are a reproducible local baseline, not a production SLO or proof
that every possible branch and tenant size has been load tested. Re-run plans
against representative tenant volumes before further index or query changes.
